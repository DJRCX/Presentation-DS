Attribute Types // ER Theory & Normalization
ER Attribute Taxonomy & Relational Implementation
Attributes are categorized by relational properties (Key, Composite, Multivalued, Derived) to satisfy First Normal Form (1NF) and ensure computational efficiency in database engines.
1. Key Attribute
Patient_ID
Uniquely identifies each patient tuple. Underlined in ER diagrams. Implemented in MySQL / MariaDB via PRIMARY KEY with NOT NULL & B-Tree index.
Patient_ID VARCHAR(20) PK UNIQUE NOT NULL
2. Composite Attribute
Address
Divisible into independent sub-components. Decomposed into distinct scalar columns (House_No, Street, City, Zip) for precise indexing and spatial queries.
Address → { House_No, Street, City, Zip_Code }
3. Multivalued Attribute
Phone_Number
A patient can hold multiple phone numbers. Storing multiple values in a single cell violates 1st Normal Form (1NF). Extracted into a dedicated child table.
Patient_Phone (Patient_ID FK PK, Phone PK)
4. Derived Attribute
Age
Dynamically calculated from Date_of_Birth. Not physically stored as a static column to prevent stale data over time. Computed during SQL queries.
Age ← TIMESTAMPDIFF(YEAR, Date_of_Birth, CURDATE())

Conceptual Model // Weak Entity Theory
Weak Entities & Identifying Relationships
A weak entity has no key attribute strong enough to guarantee uniqueness on its own. It is uniquely identifiable only in the context of its owner (strong) entity via an identifying relationship and a partial key.
Owner Entity
AMBULANCE
Weak Entity
AMBULANCE_DISPATCH
Partial Key: (Amb_ID, Dispatch_ID)
Attributes & Rule
Timestamp, Pickup_Location, Status. A dispatch record cannot exist without a registered ambulance. Deleting the ambulance cascades and removes all its dispatch logs (ON DELETE CASCADE).
Owner Entity
PATIENT
Weak Entity
PATIENT_PHONE
Partial Key: (Patient_ID, Phone)
Attributes & Rule
Phone (multivalued). A patient can hold multiple phone numbers. Extracted from PATIENT to satisfy 1NF. Cannot exist without a valid Patient_ID foreign key. (ON DELETE CASCADE).
Owner Entities
PRESCRIPTION + MEDICATION
Associative / Junction
PRESCRIPTION_MEDICINE
Composite PK: (Rx_ID, Med_ID)
Attributes & Rule
Dosage, Frequency. Resolves M:N between prescriptions and medications. A line item cannot exist without both a valid prescription and a valid medication record. Both FKs are NOT NULL.

Business Rules // Database Constraints & Conclusion
Enterprise Business Rules & Relational Constraints
Core operational constraints governing the healthcare database. Enforced directly at the engine level via Primary Keys, Foreign Keys, Unique Indexes, and NOT NULL checks.
01
One hospital can have many departments. Each department belongs to exactly one hospital.
FOREIGN KEY (Hospital_ID)
1 : N
02
A doctor can practice in multiple departments; a department employs multiple doctors.
DOCTOR_DEPARTMENT Bridge
M : N
03
A patient can make multiple appointments, each linked to one doctor and one hospital.
FOREIGN KEY (Patient, Doctor)
1 : N
04
A patient can be admitted multiple times; each admission is assigned to one specific ward bed.
FOREIGN KEY (Ward_ID)
1 : N
05
One prescription can contain multiple medications (resolved via Prescription_Medicine).
PRESC_MEDICINE Bridge
M : N
06
A hospital manages multiple ambulances; each ambulance records multiple dispatches over time.
FOREIGN KEY (Ambulance_ID)
